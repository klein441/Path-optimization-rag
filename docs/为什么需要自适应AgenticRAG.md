# 为什么需要 Adaptive Agentic RAG —— 课题《物流运输路径优化》的架构论证

> 配套文档：`docs/adaptive-agentic-rag.md`（改造方案与实施记录）
> 数据来源：`materials/课题6物流运输路径优化.docx`（课题原文）、`materials/`（原始数据）、`data/`（处理后的标准数据）
> 本文回答一个前提问题：**这个课题为什么需要 Adaptive Agentic RAG，而不是传统规则引擎 / 纯 LLM / 普通 RAG？**

---

## 1. 课题要交付什么

### 1.1 课题背景（原文第一节）

公司已形成"6 个国内基地（淄博、青州、淮北、安庆、九江、镇江）+ 3 个海外基地（越南广宁、越南清化、印尼）"的全球供应网络，外销覆盖欧洲、北美、亚太、中东，涉及海运、铁路、公路、水运等多种运输方式，还要叠加贸易条款、港口资源、关税政策与客户交付要求。系统里沉淀了订单、工厂、港口、承运商、运输费用、异常记录、客户投诉、贸易条款等大量业务数据。

### 1.2 课题目标（原文第二节）

1. 梳理国内及海外工厂的物流网络结构；
2. 分析不同工厂至不同出口港口的运输成本差异；
3. 比较海运、水运、铁路、公路等运输方式的适用场景；
4. 建立运输成本评价体系；
5. 输出最优运输路径推荐方案；
6. 为后续 AI 智能调度系统提供数据支撑。

### 1.3 预期成果（原文第七节）

《国际物流运输路径分析报告》《运输成本分析模型》《港口及运输方式对比分析》《物流路径优化方案》《运输优化建议》5 份报告 + 数据分析图表及汇报材料。

### 1.4 关键判断

课题表面是"算出一条最优路径"，但结合目标 5/6 和预期成果看，真正要交付的是：

> **把散落在多张表 + 五份报告里的优化结论，变成"可问答、可溯源、可自适应调整"的物流路径优化系统。**

"可问答"对应业务人员直接用自然语言提问；"可溯源"对应每条结论有数据/报告依据；"可自适应调整"对应随反馈持续改进、为后续 AI 调度打基础。这三条都不是传统分析方法能交付的。

## 2. 为什么传统方法不够

| 方案 | 能做什么 | 不能满足课题的点 |
|---|---|---|
| 规则引擎（现状基线） | 填表单 → 按"分配区间规则 + 费用公式"算一条最优路径 | 回答不了开放问题（对比/追问/异常解释）；无自然语言理解；结论不可溯源 |
| 纯 LLM | 能听懂自然语言 | 会编造费率/时效，**算不准钱**；无确定性内核，不可审计 |
| 传统 OR（最短路径/线性规划/多目标） | 有最优性保证 | 需要网络求解数据，而课题数据是**聚合统计**（中位数/样本数），无实时网络解；且同样无法回答自然语言问题 |
| 普通 RAG | 检索 + 生成 | 所有问题固定 top_k、固定轮数，简单问题浪费、复杂问题答不好；无反思、无降级、无学习闭环 |

课题场景的问题复杂度差异极大：

- 简单："哪些工厂生产丁腈手套？" —— 一次检索即可回答；
- 中等："1万支丁腈手套发到洛杉矶最划算" —— 需要先解析参数，再查规则/报价/费率，再算候选；
- 复杂："对比上海和宁波发到美国，直拖和海铁哪个划算？" —— 需要多轮检索 + 多工具 + 综合权衡；
- 异常："为什么查不到报价？" —— 需要判断是数据缺失还是规则不匹配，并给出可操作的答复。

没有任何单一静态方案能同时覆盖这条复杂度光谱，这就是 **Adaptive（自适应）** 的由来。

## 4. 为什么是 RAG（检索增强），而不是"把数据全喂给 LLM"

### 4.1 数据是"散装"的，任何单次 Prompt 都塞不下

- `data/`：8 张聚合表（分配规则、海运费、港杂费、拖车费、时效、港口映射、箱容、产能）+ 6 份报告；
- `materials/`：原始流水（费用 4.2MB、物料行 7.7MB、提单运单 1.6MB 等）。

一次调用不可能塞下全部数据，也不需要——RAG 按问题**只检索相关行**，再让 LLM 做权衡与解释。

### 4.2 报告里的结论要能被"用起来"

课题的五份报告包含大量已分析结论，例如：

> "长距离路线（安徽英科→上海/宁波、江西英科→上海）改海铁节省 200~3350 CNY/柜；短距离或成熟路线海铁无优势。"

这类结论原本躺在 Word 里，系统答不出。`data/report` 接入索引（`chunk_type=report`）后，用户问"海铁能省多少钱"时，系统能检索到并引用该结论。

### 4.3 课题强调"基于历史数据、可解释"

RAG 的 citations（来源/类型/分数/原文）与证据评分（`confidence`/`evidence_coverage`/`supported/missing`）把"这条结论依据哪张表、哪一行、哪份报告"显式暴露给用户，满足课题第一节"基于历史运输数据"和第七节"数据支撑"的要求。

### 4.4 幻觉控制

确定性内核（费用/时效计算、合约报价）是"硬工具"，LLM 只能调用不能捏造；`reflector` 校验所选工厂/港口必须在候选集内；`evidence.py` 按结论逐项比对证据，低置信标 `needs_review`。

## 5. 为什么是 Adaptive（自适应），而不是普通 RAG

### 5.1 复杂度分层 → 成本与延迟控制

| 问题复杂度 | 路径 | 行为 | 成本 |
|---|---|---|---|
| 低 | `fast` / `qa` | 一次检索 + 单次 LLM | 最低 |
| 中 | `agent` | 参数抽取 → 规划 → 检索 → 候选 → 反思 | 中 |
| 高（compare/exception） | `agent` + 多轮 | 多轮检索 + 恢复 + 证据收敛 | 高（只在需要时触发） |

### 5.2 可靠性兜底

- 步数上限 `AGENT_MAX_STEPS`，防止失控；
- 空候选 → 扩展检索 + 放宽条件重生成，仍无解 → 友好提示；
- 反思不通过且证据无提升 → `converge_stop` 停止空转；
- LLM 失败 → 自动降级规则引擎；embedding 缺失 → 哈希向量回退；
- 低置信 → `needs_review`（需人工复核）或反问澄清 `requires_clarification`。

### 5.3 学习闭环（课题目标 6）

`recommendation_feedback` 记录用户"确认/改选/费用修正"，`FEEDBACK_AUTO_APPLY=true` 时按反馈调整候选评分与费用，推荐随使用持续改进——这正是"为后续 AI 智能调度提供数据支撑"的雏形。

### 5.4 多轮会话与 LLM 路由

- 会话记忆：用户说"那发到纽约呢"时继承上轮的"产品/数量"并覆盖目的港（`session_store.py`）；
- LLM 路由：关键词无法定意图时（如"MSC 和 COSCO 哪个快"）用 LLM 分类，避免误判（`router.py` 的 `routed_by: llm`）。

## 7. 一条请求如何被"自适应"处理（实测示例）

| 用户输入 | 路由结果 | 关键行为 |
|---|---|---|
| 哪些工厂生产丁腈手套？ | `consult / qa` | 一次检索 + 生成，`confidence 0.8` |
| 1万支丁腈手套发到洛杉矶最划算 | `natural_recommend / agent` | `extract_params` 抽取产品/数量/目的港/偏好 → 检索 → 候选 → 反思，`confidence 0.98 / coverage 1.0` |
| 那发到纽约呢（同一会话） | `natural_recommend / agent` | 会话记忆继承产品/数量，规则覆盖目的港 → 江西英科→纽约 |
| MSC 和 COSCO 哪个快 | `compare / agent`（`routed_by: llm`） | 关键词未命中 → LLM 路由分类 |
| 帮我推荐 | `natural_recommend / agent` | 参数缺失 → `requires_clarification` 反问 + `needs_review` |

## 8. 诚实边界

- **如果目标只是交一份分析报告**：传统 ETL + 规则引擎 + 人工写报告就够，不需要这套架构；
- **如果要交付"可问答的智能优化系统"**：业务人员直接提问、看到依据、能反馈修正——Adaptive Agentic RAG 才是必要且合理的；
- **成本说明**：需要 LLM API Key（可降级为规则引擎）；语义向量为可选开关（默认哈希回退）；多轮 Agent 只对复杂问题触发，简单问题走快速路径控制成本。

## 10. 结论

这个课题的本质不是"求一次最优解"，而是**把历史数据与分析结论变成可持续问答、可溯源、可自适应的优化系统**。规则引擎算得准但答不了开放问题，纯 LLM 听得懂人话但会编数字，普通 RAG 不做复杂度分层也没有可靠性兜底。Adaptive Agentic RAG 用"分层路由 + 检索增强 + 确定性内核 + 反思校验 + 证据评分 + 反馈闭环"同时满足课题对**准确性、可解释性、成本可控、持续改进**的要求——这正是本项目选择它的原因。
