## 第 1 页 · 封面

**物流路径优化 · 自适应 Agentic RAG 智能问答系统**
——让“1 万支丁腈手套发洛杉矶最划算从哪走？”这样的业务问题，得到可溯源、可自适应、可学习的答案

- 项目定位：面向国际物流业务的智能优化系统，把散落在多张 Excel、五份分析报告、原始数据里的优化结论，变成**可问答、可溯源、可自适应调整**的知识系统
- 核心能力：知识问答 / 智能推荐 / 港口与工厂对比 / 加急时效 / 数据异常解释
- 一句话价值：**业务人员直接问自然语言，系统给出带依据的最优物流方案，并随反馈持续变聪明**
- 技术底座：Adaptive Agentic RAG（自适应 + Agent 编排 + 检索增强生成）

> 讲稿：大家好，今天介绍我们基于“自适应 Agentic RAG”改造的物流路径优化系统。过去系统只能“填好表单给一条最优路径”，现在我们把它升级成能听懂业务人员自然语言提问、能给出依据、还能自我改进的智能问答系统。

## 第 2 页 · 什么是 Adaptive Agentic RAG

**从 RAG 到 Agentic RAG 到 Adaptive：三个层次的进化**

| 层次 | 做法 | 局限 |
|---|---|---|
| 传统 RAG | 固定检索 Top-K → 拼进 Prompt → LLM 生成 | 所有问题同一套参数，简单问题浪费算力、复杂问题答不全 |
| Agentic RAG | LLM 自主规划：先查工厂规则、再查海运费、再算费用，多步执行 + 反思 | 会“编数字”，需要工具与校验约束，成本高 |
| **Adaptive Agentic RAG** | 按问题复杂度**自适应**选路径/调检索参数/控制轮数/降级人工 | 简单问题走快速路径省钱，复杂问题走多步 Agent，低置信交人工 |

**关键设计三问（Adaptive 的落点）**
- **查不查？查什么？查几轮？** —— 由查询路由器 + 检索画像 + 证据评分共同决定
- **哪些结论能被证据证明？** —— 每个回答附 `citations`（引用依据）+ `confidence`（置信度）+ `evidence_coverage`（证据覆盖率）
- **什么时候停止 / 降级 / 交给人工？** —— 反思器不通过就补检重算；仍不达标就 `needs_review` 交人工复核；关键参数缺失就反问澄清

> 讲稿：Adaptive Agentic RAG 不是新技术名词堆叠，它回答的是业务系统最现实的问题——问题复杂度差异极大，不能一套参数打天下。我们的系统里，“哪些工厂产丁腈手套”走快速问答，“对比五个港口三种条款的综合成本”走多步 Agent，答不出来的就交给人工。

## 第 3 页 · 为什么这个项目需要它

**课题背景：materials/课题6 物流运输路径优化 —— 目标不是“算一条最优路径”，而是“让优化结论可问答、可溯源、可自适应”**

- 规则引擎只能“填好表单给一条最优路径”，答不了五类开放问题
- 纯 LLM 会编造费率/时效，算不准钱
- 数据是“散装”的：8 张聚合表 + 五份报告 + materials 原始数据，任何单次 Prompt 都塞不下

**系统必须回答的五类问题**
- **查**：哪些工厂产丁腈？FOB 和 DDP 有什么区别？→ `consult`
- **推**：1 万支丁腈手套发洛杉矶最划算从哪走？→ `natural_recommend`
- **比**：上海 vs 宁波、直拖 vs 海铁哪个划算？→ `compare`
- **急**：赶船期去美国要几天？→ `urgent`
- **异常**：为什么查不到某条路线报价？→ `exception`

**为什么是 RAG 而不是“直接把数据喂给 LLM”**
- 五份报告的优化结论（如“海铁长距离省 200~3350 CNY/柜”）躺在 Word 里，RAG 把它们变成可检索知识
- 数据按需检索相关行，LLM 只做权衡与解释，数字来自成本引擎不靠编
- 课题强调“基于历史数据、可解释”——citations / 证据评分正好回答“这条结论依据哪张表哪一行”

> 讲稿：这个课题要交付的不是一份静态报告，而是一个“业务人员能直接问、能看到依据、能反馈修正”的智能系统。Adaptive Agentic RAG 的结构——知识层、推理层、学习层——正好对应课题里“数据体系→成本建模→路径优化→效果评估”的落地实现。

## 第 4 页 · 系统总体架构

**四层架构：知识层 → 检索层 → Agent 推理层 → 自适应学习层**

```
用户 / 前端 (front/rag.html 对话入口)
        │
  查询理解与路由 Router（intent + 复杂度）
        ├─ 简单/标准查询 ──► 快速路径：规则 + 混合检索（省钱省时）
        └─ 复杂/多步查询 ──► Agent 编排：规划 → 工具 → 反思 → 恢复
                                │
   检索层 Retriever：结构化知识 + 关键词 + 向量 融合检索（自适应 Top-K / 重排）
        │
   知识层：KnowledgeBase（122 国/港口/工厂/条款/箱容）
          + RagStore（Excel 规则报价费率 + data/report 报告，7444 chunks）
          + 规则引擎 CostCalculator / route_pricing（费用与时效只算不编）
        │
   反思校验 Reflector + 证据评分 Evidence（citations / confidence / needs_review）
        │
   结果：结构化推荐 JSON + reasoning + citations + 置信度
        │
   学习层：会话记忆 session_store + 反馈闭环 recommendation_feedback → 调权 → 回流路由/排序
```

**一次复杂请求的链路（“美国 800 箱丁腈手套赶 8 月底船期，DDP”）**
1. 路由识别：标准推荐 + 时效敏感 + DDP → Agent 路径，Top-K 调大
2. 混合检索：工厂分配规则 + 合约海运费 + DDP 历史方案
3. 规划执行：锁工厂 → 取最便宜 5 港 → 算全费用 → 核船期
4. 反思校验：能否赶 8 月底？DDP 可用？不满足则补检重算
5. 结果生成：JSON + reasoning + risk_warning + citations，全程可溯源
6. 反馈落库：用户确认/改选/费用修正 → 回流排序权重

> 讲稿：系统分四层。上层是自适应开关，中层是检索与 Agent 推理，底层是权威数据和确定性计算引擎。特别注意：费用和时效这些数字全部来自成本引擎，LLM 只负责权衡与解释，这是防幻觉的关键。

## 第 5 页 · 核心功能

**1. 三类路径自适应（查不查、查几轮）**
- `fast` 快速路径：简单查询一次检索 + 单次 LLM，省成本
- `agent` Agent 路径：规划-执行-反思循环，多轮恢复直到证据达标或收敛停止
- `qa` 纯知识问答：术语 / 概念 / 时效咨询直接回答

**2. 七类意图路由**
- `consult` 知识咨询、`standard_recommend` 表单推荐、`natural_recommend` 自然语言推荐
- `compare` 港口/工厂真对比（上海 vs 宁波：含海运费合计成本排序输出对比表）
- `urgent` 加急时效、`exception` 无报价异常解释、`follow_up` 多轮追问（“那发纽约呢”）

**3. 结果可信与可溯源**
- 每条回答附 `citations` 引用依据（知识库/报告/报价来源）、`agentTrace` 执行轨迹
- `confidence` 置信度 + `evidence_coverage` 证据覆盖率 + `needs_review` 人工复核标记
- 关键参数缺失时 `requires_clarification` 反问澄清，不硬猜

**4. 学习与记忆**
- 会话记忆：多轮参数继承、上一轮推荐注入上下文
- 反馈闭环：用户确认 / 改选 / 费用修正 → `feedback_weights.py` 调权 → 排序回流
- LLM 路由：意图模糊时由 LLM 分类（`routed_by: keyword|llm`）

**5. 工程特性**
- 零重依赖降级：无 chromadb/langgraph 也可运行；`RAG_ENABLED=false` 完全回退旧流程
- 真实业务修复：术语误路由、工厂 chunk 霸榜、时效咨询误进 urgent、compare 未真对比等均已在迭代中修复

> 讲稿：功能上我们坚持“能算的不让 LLM 编”。比如对比题，系统会按问题中的港口分别取最便宜候选，把 FOB 费用和合约海运费叠加排序，输出对比表而不是让模型拍脑袋。

## 第 6 页 · RAG 四指标评测（严格口径）

**评测口径（docs/rag-eval-report.md，黄金测试集 9 题 + LLM 判分核验）**
- 为避免指标虚高，采用严格口径：Recall 拆「纯检索 / 总」两列（剔除规则注入 chunk）、Precision 需命中 ≥2 个相关词、Faithfulness 用 **LLM 句子级逐句核验**（替代“引用自证”）

**当前真实成绩（严格口径）**

| 指标 | 定义 | 成绩 |
|---|---|---|
| Recall（纯检索） | 标准答案信息有多少被**真实检索**到（不含规则注入） | **66.7%** |
| Recall（总） | 含结构化规则注入的召回 | 100% |
| Precision（≥2词） | 检索到的 chunk 有多少真正相关 | **75.7%** |
| Faithfulness（LLM句子级） | 答案陈述逐句是否有检索证据支撑 | **62.8%** |
| Answer Relevance | 答案是否真正回答了问题 | **约 70%** |

**为什么之前显示 100% 是虚高（已修正口径）**
- Recall 100% 中约 1/3 的“命中”来自规则主动注入的工厂/国家/条款/合约费率 chunk（score=1.0 恒排最前），不是检索能力——纯检索口径下 q06 推荐题甚至只有 0%
- Precision 93.7% 是被“命中 1 个宽泛词即算相关”撑起来的（词表里全是 美国/海运/天）
- Faithfulness 100% 是“用生成答案所用的同一段上下文自证 + 数字全豁免”的结构性结果，不是真的无幻觉

**逐题暴露的真实短板（也是改进方向）**
- 推荐/对比类（q06/q08）：关键事实（青岛/上海/MSC 2102）只能靠注入拿到，语义/关键词检索没抓到报价 chunk
- 加急类（q07）：Precision 25%、Relevance 27.5%——答案模板未直接回答“最快几天”，且检索命中差
- 异常类（q09）：Faithfulness 0%——兜底提示语是规则逻辑推断，没有检索证据支撑（结论本身合理，但无证据链）

> 讲稿：我们对评测做了“去水”：把规则注入和真实检索分开算、用 LLM 逐句核验忠实度。修正后的真实水平是——纯检索召回约 67%、精确率约 76%、忠实度约 63%、相关性约 70%。这个数字不可爱但真实，它直接告诉我们下一步该补什么：向量化检索和重排、以及更完整的证据链。

## 第 8 页 · 未来数据补充与改进方向

**一、数据内容补充（让答案更精确、更全）**
- **接入 materials 原始数据**：订单、提单、费用明细、船期明细做 ETL 清洗 → 结构化进知识库，支撑“按历史订单精确回答/统计”（当前只用处理后的聚合表，原始明细可回答“某条路线历史上真实走了多少次、费用分布如何”）
- **实时/新鲜数据**：海运费合约有效期与实时报价刷新、汇率每日同步、船公司船期准点率
- **时效样本扩容**：目前部分路线样本数=1，需补足到可估计 P10/P90 的样本量；覆盖更多 起运港×目的港 组合
- **多语言与术语**：贸易条款、报关单证等英文术语对照；FOB/DDP 等条款维度对比数据
- **标注数据**：真实问答对（业务人员提问+专家答案）扩充评测集，覆盖更多边界场景

**二、检索与模型改进**
- 启用真实语义向量（`RAG_EMBEDDING_ENABLED`，bge-small-zh）与 bge-reranker 重排，替换哈希向量回退
- 真实向量库（Qdrant/Chroma）替换内存索引，支持大规模数据与增量更新
- 检索评估自动化：评测集扩到几十题，接入 CI 每次改动跑四指标回归

**三、Agent 与交互改进**
- `urgent` 专用答案模板（直接回答“最快几天、最稳哪条线”），提升加急类相关性
- 多轮 Agent 编排升级（LangGraph）与可观测面板；反馈调权从“调分”细化到“调费率/时效权重”
- 模型路由：低风险问题用小模型、高价值问题用强模型，进一步控制成本

**四、落地路径建议**
- Phase 1：materials 原始数据入知识库 + 评测集扩充（数据优先）
- Phase 2：向量化 + 重排 + 真实向量库（检索质量）
- Phase 3：urgent 模板 + 反馈调权细化 + 可观测面板（体验与学习闭环）

> 讲稿：未来的核心不是堆模型，而是补数据——把 materials 原始明细做成可检索的结构化知识，让系统从“知道规则”进化到“看过真实历史订单”；再配合向量化与重排把检索质量提上去，最后把反馈闭环做得更细。这样一个“问得出、查得到、算得准、学得会”的物流智能问答系统就闭环了。
